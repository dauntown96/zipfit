- 「원문에서 찾은 행」은 행 `content_raw` 첫 줄 24자(공백·기호를 뺀 것)가 원문 문단에 처음 나오는 자리를 찾은 수다. 처음 나오는 자리라서 첫 장 요약 상자에 붙은 행이 있다(울산 「1. 건설위치」 15행이 그 꼴이다). **위치 대조는 근삿값**이다.
- **`seq`는 원문 순서를 거의 지킨다**(이웃 쌍 중 뒤집힘 2~13%).
- **화면은 그 순서를 버린다.** `zfPolicyBodyHtml`(`index.html` 10995~10997)은 고정 행(⚠️ · 정정 · 모집 일정)을 빼고 나머지를 `category` **가나다순**으로 정렬한다(`localeCompare(…,'ko')`). 그 뒤 사용자 칩 9개 묶음으로 다시 가른다(`zfPolListHtml`). 그래서 이웃 쌍의 32~50%가 원문과 거꾸로 선다.
  - 스킬 191은 「`order=category,seq`」라고 적고 있다. 실제 화면은 seq를 쓰지 않는다.
- **원문 1층 절 → 우리 행 짝**:
  - 빈 절이 있다: 김해 「6. 모집일정」(일정 표 `announcement_schedule`로 감) · 울산 「9. 주택성능등급」 · 익산 9~12(시행자 · 붙임 셋) · 충북 1·11·12·17·18·19.
  - 일부는 세대 표(`housing_units`)나 일정 표로 간 것이고, 일부(시행자 · 성능등급 · 붙임)는 싣지 않은 것이다.
  - 쪼개짐: 한 절이 7~16행(「신청자격」 · 「유의사항」)이 된다.
  - 합쳐짐은 드물다(행 = 문단 하나).
- **표**: 원문 표는 「열 머리 : 값」 줄로 풀려 한 행에 들어간다. 그런 줄이 3개 이상인 행은 표본마다 5~26행이고, 전체로는 **3,967 / 15,980행(24.8%)**이다. 화면은 `white-space:pre-wrap` 글자로만 그린다. 칸 경계·병합·머리줄은 남지 않는다.
- **강조**: `content_raw`는 글자만 담는다. 굵게·색·밑줄은 **0% 남는다**. 글머리표(①·•·-·■)와 `※`는 글자라서 남는다. `※`가 든 행은 표본마다 7~26행이고, 전체로는 3,933행이다.
- **층위**: 칸이 없다. `category`가 대개 2층 `■` 이름이거나 표 행 레이블이다. 1층 제목과 같은 이름은 표본 행의 0~20%뿐이다.

## 6. Claude Code 의견

### 왜 원문보다 읽기 어려운가 — 보는 대로

1. **차례가 깨진다.** 원문은 「누가 → 어떻게 고르나 → 언제 → 어떻게 내나」로 흐른다. 화면은 그 흐름을 가나다순과 칩 9개로 다시 섞는다. 이웃 쌍의 3~5할이 거꾸로 선다. 「소득 기준」 다음에 「문의처」가 오고, 「배점」이 「순위」보다 앞에 선다. **가장 큰 원인이고, 데이터 없이 고칠 수 있다**(`seq` 순).
2. **층이 하나다.** 원문은 4~5층(큰 상자 → ■ → ①·• → ※)이다. 화면은 같은 크기 아코디언 30~80개를 한 줄로 늘어놓는다. 제목도 1,905가지 이름표라 같은 「소득·자산 산정방법」이 점 글자 셋으로 갈린다.
3. **표가 글이 된다.** 행의 25%가 「머리 : 값」 줄이다. 칸을 눈으로 맞춰 보던 원문보다 비교가 어렵다.
4. **강조가 사라진다.** 원문은 문단의 23~42%를 굵게 하고, 붉은 글자로 「금회 한정」·기한을 짚는다. 우리 화면은 모든 글자가 같은 무게다.
5. **요약 상자가 섞인다.** 첫 장 「매우 중요한 사항」(262행)이 본문 절과 같은 자리에 서서 같은 말이 두 번 보인다.

### 공고 상세의 고정 절 순서 — 안

요청서 안(누가 → 언제 → 얼마 → 어떻게 → 서류 → 주의)에 대체로 동의한다. 다만 둘을 바꾸기를 권한다.

**권하는 순서**: ① 누가(신청자격 · 소득·자산) → ② 얼마(공급 대상·임대조건) → ③ 언제(일정) → ④ 어떻게(신청 방법 · 서류 제출) → ⑤ 서류 → ⑥ 어떻게 뽑나(순위·배점·선정) → ⑦ 발표·계약·입주 → ⑧ 주의(유의사항 · ⚠️) → ⑨ 붙임(주택소유 판정 · 산정방법 · 장애 정도) → 문의처.

- (가) 「얼마」를 「언제」 앞에 둔다. 신청자는 「되나」 다음에 「얼마인가」로 거르고, 그다음에 날짜를 본다. 표본 7건 중 5건이 임대조건을 일정보다 앞에 둔다.
- (나) 「어떻게 뽑나(선정)」를 따로 한 절로 세운다. 원문 7건 모두에 있는 공통 절이고, 지금은 「자격·소득」과 「선정·배점」 칩으로 흩어진다.
- 이 9절은 1-4 공통 절과 그대로 짝이 맞는다. 원문 1층 제목 → 고정 절 사상은 1층 제목이 7~19개뿐이라 손으로 해도 작다. 절 안은 **원문 경로와 원문 차례 그대로** 둔다.

### 원칙 「사실은 원문 · 표현은 꼭집 말」 안에서

| 할 수 있다 | 할 수 없다 |
|---|---|
| 절 순서 · 묶음 · 목차 이름 · 아이콘(꼭집 말 → 「AI 정리」 표시) | 원문 문장을 고쳐 쓰기 · 두 원문 행을 한 문장으로 합치기 |
| 원문 표를 칸 그대로 다시 그리기(값은 원문 글자) | 표 값 반올림 · 단위 바꿈 밖의 변환 |
| 원문이 굵게 한 글자를 굵게(사실) | 우리가 고른 「중요」를 원문 강조처럼 보이기 — 그것은 「AI 정리」 표지와 함께만 |
| 「나에게 해당하는 절만」 거르기(원문 계층 이름으로) | 원문에 없는 「해당 없음」 판정을 사실처럼 쓰기 |
| 같은 뜻 category를 한 목차 이름 아래 모으기 | category 원문 이름 지우기(행 머리에는 원문 이름을 둔다) |

### 무엇부터 — 화면 한 수 먼저, 그다음 데이터와 같이

1. **화면 먼저, 데이터 0**: 정책 절의 정렬을 가나다순에서 `seq`(원문 차례)로 바꾸고, 고정 9절 목차를 category → 표준 분류 사상(이미 있음)으로 붙인다. 작고 되돌리기 쉽고, 1번 원인(차례)을 바로 줄인다.
2. **데이터**: `section_path`·`depth`를 스킬에 더하고(작은 개정), 열린 101공고에 기계 대조로 소급한다(79% 자동). 이것이 서면 목차 바로가기와 「원문 몇 절」 표지가 정확해진다.
3. **데이터 + 화면**: 표 칸(④)과 원문 강조(⑤)를 hwpx 공고부터.
4. ⑦ 「누구에게 해당」은 그 뒤 — 손이 가장 많이 든다.

- 걱정: 고정 9절로 모으면 공급기관마다 다른 원문 순서가 사라진다. 「원문 차례로 보기」 스위치를 같이 두기를 권한다(요점 끄기 스위치와 같은 꼴).
- 「매우 중요한 사항」 요약 상자 행은 ⑧ 주의 절 맨 위나 카드 1층으로 따로 두는 것이 좋겠다. 본문 절에 섞지 않는다.
